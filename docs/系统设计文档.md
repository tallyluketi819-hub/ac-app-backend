## 1. 系统架构设计

### 1.1 整体架构概述

本系统采用**前后端分离**的经典三层架构，前端为微信小程序，后端为基于 Node.js + Express 构建的 RESTful API 服务，数据持久层使用 MySQL 关系型数据库。三层之间通过标准 HTTP 协议进行通信，数据格式统一采用 JSON。

```
┌─────────────────────────────────────┐
│         微信小程序（前端）            │
│  ┌──────────┐  ┌──────────────────┐ │
│  │  页面层   │  │    逻辑层（JS）   │ │
│  │  WXML/   │  │  API请求封装      │ │
│  │  WXSS    │  │  状态管理         │ │
│  └──────────┘  └──────────────────┘ │
└──────────────┬──────────────────────┘
               │  HTTPS / JSON
               ▼
┌─────────────────────────────────────┐
│       Node.js + Express（后端）      │
│  ┌──────────┐  ┌──────────────────┐ │
│  │  路由层   │  │    业务逻辑层     │ │
│  │  Router  │  │   Controllers    │ │
│  └──────────┘  └──────────────────┘ │
│  ┌──────────────────────────────┐   │
│  │       中间件层                │   │
│  │  JWT鉴权 / 错误处理 / 日志    │   │
│  └──────────────────────────────┘   │
└──────────────┬──────────────────────┘
               │  mysql2 驱动
               ▼
┌─────────────────────────────────────┐
│           MySQL 8.0（数据库）        │
│   users / bills / groups /          │
│   group_members / group_bills /     │
│   debts                             │
└─────────────────────────────────────┘
```

### 1.2 技术选型说明

| 层次 | 技术方案 | 选型理由 |
|------|----------|----------|
| 前端框架 | 微信小程序（原生） | 覆盖微信生态，无需安装，天然契合目标用户群体的使用习惯 |
| 后端运行环境 | Node.js v18 LTS | 事件驱动、非阻塞I/O，适合高并发 API 场景；JavaScript 全栈降低学习成本 |
| 后端框架 | Express 4.x | 轻量灵活，中间件生态丰富，适合中小型 RESTful API 项目 |
| 数据库 | MySQL 8.0 | 成熟稳定的关系型数据库，天然支持事务，适合账务类数据的一致性要求 |
| 数据库驱动 | mysql2 | 支持 Promise/async-await，性能优于 mysql 包 |
| 身份鉴权 | JWT (jsonwebtoken) | 无状态鉴权，适合前后端分离架构，避免服务器存储 Session |
| 密码加密 | bcrypt | 行业标准密码哈希算法，内置 salt，安全性高 |
| 接口风格 | RESTful | 语义清晰，易于维护和扩展 |

## 2. 模块设计

### 2.1 功能模块总览

系统共分为四个业务模块，各模块相互独立，通过统一的用户身份（user_id）进行关联。

```
┌────────────────────────────────────────────────┐
│              校园记账微信小程序                   │
├──────────┬──────────┬──────────┬───────────────┤
│  用户模块 │  账单模块 │ AA分账模块│ 校园消费画像  │
├──────────┼──────────┼──────────┼───────────────┤
│ 注册登录  │ 新增账单  │ 创建群组  │ 消费健康评分  │
│ 个人资料  │ 账单列表  │ 成员管理  │ 同校消费对比  │
│ 修改信息  │ 月度统计  │ 群组账单  │ 消费结构分析  │
│ 退出登录  │ 编辑删除  │ 债务计算  │ 同校统计概览  │
│          │          │ 债务结清  │               │
└──────────┴──────────┴──────────┴───────────────┘
```

### 2.2 各模块职责描述

- **用户模块：** 负责用户身份的注册、认证与信息管理。提供 JWT 令牌的签发与校验，是其他所有模块正常运作的前提。

- **账单模块：** 负责个人收支记录的增删改查，以及按月维度的统计汇总。是系统的核心功能模块，所有账单数据与用户绑定，严格数据隔离。

- **AA分账模块：** 负责群组的生命周期管理（创建、加入）、群组共同支出的记录，以及基于净额轧差算法的债务关系计算与结清管理。

- **校园消费画像模块：** 以匿名聚合方式使用同校用户的消费数据，为当前用户生成个性化的消费健康评分和横向对比报告。

| 字段名 | 类型 | 说明 | 约束 |

| from_user_id | INT | 债务人（欠钱方）的用户ID，外键 | NOT NULL, FOREIGN KEY → users(id) |
| to_user_id | INT | 债权人（收钱方）的用户ID，外键 | NOT NULL, FOREIGN KEY → users(id) |

| created_at | DATETIME | 债务生成时间 | DEFAULT CURRENT_TIMESTAMP |

### 3.7 E-R 关系描述

各实体间的关系如下：

- **users ↔ bills（一对多）：** 一个用户可以拥有多条个人账单，每条账单必须归属于一个用户（`bills.user_id → users.id`）。
- **users ↔ groups（一对多）：** 一个用户可以创建多个分账群组，每个群组有且仅有一个创建者（`groups.creator_id → users.id`）。
- **users ↔ groups（多对多）：** 一个用户可以加入多个群组，一个群组可以包含多个用户，通过 `group_members` 表进行关联。
- **groups ↔ group_bills（一对多）：** 一个群组可以包含多条群组账单，每条群组账单归属于一个群组（`group_bills.group_id → groups.id`）。
- **group_bills → debts（一对多）：** 每次新增群组账单后，系统根据分摊逻辑生成或更新对应的债务记录，存储于 `debts` 表。
- **users ↔ debts（一对多）：** 一个用户可以在多条债务记录中作为债务人或债权人出现。

## 4. 接口设计概述

### 4.1 设计风格

本系统后端接口遵循 **RESTful** 设计风格，以资源为核心组织 URL 路径，使用 HTTP 标准动词（GET / POST / PUT / DELETE）表达操作语义。

### 4.2 统一响应格式

所有接口统一返回以下 JSON 格式，前端可通过 `success` 字段判断请求是否成功：

```json
{
  "success": true,
  "data": { ... },
  "message": "操作成功"
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| success | Boolean | 请求是否成功：true / false |
| data | Object / Array / null | 响应业务数据，失败时为 null |
| message | String | 人类可读的操作结果描述或错误原因 |

### 4.3 JWT 鉴权机制

需要身份验证的接口，客户端须在 HTTP 请求头中携带 Authorization 字段：

```
Authorization: Bearer <token>
```

服务端通过自定义中间件 `authMiddleware` 对 Token 进行验证：解析 Token 中的 `userId` 信息，并注入到 `req.user` 对象供后续控制器使用。Token 有效期为 **7天**，过期后需重新登录获取新 Token。

### 4.4 错误处理规范

| HTTP状态码 | 含义 | 典型场景 |
|------------|------|----------|
| 200 | 请求成功 | 正常业务响应 |
| 400 | 请求参数错误 | 缺少必填字段、格式不合法 |
| 401 | 未授权 | Token缺失、Token过期或非法 |
| 403 | 禁止访问 | 无权限操作他人数据 |
| 404 | 资源不存在 | 查询的账单或群组不存在 |
| 500 | 服务器内部错误 | 数据库异常或代码错误 |

## 5. AA分账算法设计

### 5.1 问题描述

在多人分账场景中，若多笔账单由不同人付款、参与者各异，直接记录两两之间的欠款关系会产生大量冗余债务条目，转账次数多且关系复杂。例如，A欠B 30元、B欠C 20元，实际最优方案是A直接转给C 20元，A转给B 10元，即可完成所有结算。

### 5.2 净额轧差算法

本系统采用**净额轧差（Net Settlement）**算法将群组内的复杂债务关系化简为最少笔数的转账方案，核心步骤如下：

**步骤一：计算每个成员的净余额**

对群组内所有账单进行遍历，按如下规则计算每位成员的净余额：
- 若某成员为付款人，则其净余额 **加上** 其他参与者应分摊的金额。
- 若某成员为参与者，则其净余额 **减去** 应分摊金额。

净余额为正 → 该成员为净债权人（需要收钱）
净余额为负 → 该成员为净债务人（需要还钱）
净余额为零 → 该成员无需额外转账

**步骤二：贪心匹配，生成最少转账方案**

将所有成员按净余额排序，维护两个队列（债权队列和债务队列），通过贪心匹配的方式逐步消除债务：

```
while 债务队列非空 and 债权队列非空:
    取债务最大者（debt_max）和债权最大者（credit_max）
    转账金额 = min(|debt_max|, credit_max)
    记录债务：debt_max → credit_max，金额为 transfer_amount
    更新两者净余额，移除净余额为0者
```

### 5.3 算法效果

通过净额轧差，N个成员之间的债务关系最多只需 N-1 笔转账即可完成全部结算，相比两两直接结算（最多 N*(N-1)/2 笔）大幅减少转账次数，提高结算效率。

## 6. 校园消费画像算法设计

### 6.1 消费健康评分模型

消费健康评分旨在衡量用户消费结构的合理性，满分100分，基础分60分，各维度根据表现进行加减分。评分每月自动更新一次。

| 评分维度 | 说明 | 加分规则 | 扣分规则 |
|----------|------|----------|----------|
| 餐饮支出占比 | 餐饮消费占总支出比例 | 占比30%~50%：+10分 | 占比>70%：-10分 |
| 学习支出占比 | 书籍、课程等学习消费占比 | 占比>10%：+10分 | 占比<3%：-5分 |
| 娱乐支出占比 | 游戏、电影等娱乐消费占比 | 占比5%~15%：+5分 | 占比>30%：-10分 |
| 当月是否有结余 | 收入大于支出 | 有结余：+10分 | 支出超出收入50%以上：-15分 |
| 记账连续性 | 当月记录天数 | 记录≥20天：+5分 | 记录<5天：-5分 |

**最终评分 = max(0, min(100, 基础分60 + 各维度加减分总和))**

### 6.2 同校对比数据

系统以"学校"为维度，对同校用户的当月消费进行匿名聚合统计，计算各类别的**平均值**和**中位数**，供个人与之对比，识别自身在同校群体中的消费位置（偏低/正常/偏高）。

## 7. 安全设计

### 7.1 密码安全

用户密码在存储前必须经过 **bcrypt** 算法进行哈希加密处理，加密轮数（saltRounds）设置为10。系统任何模块均不存储、传输或展示用户明文密码。登录时通过 `bcrypt.compare()` 方法对输入密码与数据库中的哈希值进行验证。

### 7.2 JWT Token 管理

- Token 由服务端签发，内容包含 `userId` 和签发时间，使用服务端私钥（存储于环境变量 `JWT_SECRET`）进行签名。
- Token 有效期设置为 **7天**，超期后自动失效，前端需引导用户重新登录。
- 服务端不维护 Token 黑名单（无状态设计），用户"退出登录"操作由前端清除本地存储的 Token 实现。

### 7.3 接口鉴权

所有涉及用户数据的接口均通过 `authMiddleware` 中间件进行鉴权，鉴权失败时统一返回 HTTP 401 状态码。控制器层在处理涉及特定资源（如账单、债务）的操作前，额外校验资源的所有者（`user_id`）是否与当前登录用户一致，防止越权访问。

### 7.4 数据隔离

- 个人账单查询时，SQL 语句强制附加 `WHERE user_id = ?` 条件，确保用户只能访问自己的数据。
- 校园画像接口返回的同校数据为聚合统计结果，不含任何可识别个人身份的字段。
